# Versioned Graph Settings

*For system administrators, workspace administrators and data owners.*

Every setting that decides how versioned graphs are read, updated, built, kept in memory, drafted and imported: what each one means, what it changes, when to change it, and what we recommend. System administrators set them under **Admin → Versioned graphs**; a workspace's own values and one graph's are set from the workspace and the data source.

> **Note:** This page is generated from the settings registry in the code by `backend/scripts/export_settings_reference.py`, which also writes the catalogue the app shows. Don't edit it by hand: change the registry, run `python3 backend/scripts/export_settings_reference.py` and commit the result. CI fails when this page is out of date.

## How these settings work

### Where a value comes from

Each setting has one value in force for each graph. It comes from the most specific level that chose one:

1. **Graph**: one data source's graph. A fork follows the graph it was forked from.
2. **Workspace**: every graph in the workspace.
3. **Platform**: every graph.
4. **Default**: the deployment's environment variable if it is set and valid, else the built-in value.

So a graph with nothing of its own takes its workspace's value, else the platform's, else the default. The app shows the whole trail, Default → Platform → Workspace → Graph, with the level in force highlighted.

### Who may set what

- **System administrators** set the platform's values, and may set any level.
- **Workspace administrators** set their workspace's values and their graphs', for the settings marked so below.
- Settings that spend the graph store's memory or the database's capacity are system administrators' only, at every level: Updates & loading, New-version builds, Memory & residency (the residency class too), Database reads, and Matching properties per graph.

### Limits and exceptions

A system administrator can limit what workspace administrators choose:

- **Allowed choices**, such as which read modes a workspace may pick. By default workspaces may choose Always the latest or Keep serving, update in place.
- **A range**: the lowest and highest number allowed.
- **A lock**: the platform's value holds everywhere, and lower levels can't change it.

A value a system administrator sets outside the limits stays in force, marked as an exception, so tightening a limit never changes a graph without anyone noticing.

### When a change takes effect

A saved value reaches every process within a few seconds. Each setting below says when it is then acted on: at the next read, the next write, the next memory check, the next sweep or the next import.

### Saving a change

Nothing is saved until you review it: each value before and after, what the change does to your graphs, and a reason, which the history keeps. A change that removes what can't be brought back (the changes of closed drafts the next sweep would remove), or that moves a high-risk setting the riskier way, must be acknowledged first. The settings API refuses such a save (`409 acknowledgement_required`, naming each warning) unless its request lists the warnings' codes in `acknowledge`.

### Why a value differs from the one chosen

When the value in force isn't the one chosen, the app says why:

| Reason | What it means |
|---|---|
| `switch_off` | A feature switch this setting needs is off, so it has no effect until the switch is on. |
| `builds_off` | Keep serving, switch when ready needs New-version builds, which is off, so updates are written in place until it is on. |
| `connected_graph` | This is a connected graph: its copy belongs to its owner, so it is never copied or built beside, and it updates in place. Adopting it onto a platform copy changes that. |
| `not_used_by_mode` | Not used: the read mode in force is Always the latest, which never serves an older version. |
| `capped_by_deployment` | Your deployment caps this value, so the cap is in force. |
| `capped_by_setting` | Another setting caps this value, so the lower one is in force. |
| `locked_by_platform` | A system administrator locked this setting for the whole platform, so the platform's value is in force. |
| `outside_limits_exception` | This value is outside the limits set for workspaces. A system administrator chose it, so it stays in force as an exception. |
| `invalid_env` | The deployment's environment value isn't valid, so the built-in default is in force. |
| `env_out_of_range` | The deployment's environment value is outside this setting's range, so the nearest allowed value is in force. |
| `follows_root` | A fork follows the graph it was forked from: change this on that graph. |
| `derived_from_levels` | Only one draft level is allowed, so new drafts start at that level. |
| `guard_off` | The replace guard is off, so this limit isn't checked. |

## Reads & consistency

What people see while new data loads, and how far behind a fast view may be.

**With the defaults:** Readers get Always the latest: the newest version as soon as it is published, read from the database while the graph store catches up.

| Setting | Default | Set at |
|---|---|---|
| [Read mode](#reads-mode) | Always the latest | Platform, Workspace, Graph |
| [Most versions behind](#reads-maxversionsbehind) | Unlimited | Platform, Workspace, Graph |

### `reads-mode`

**Read mode.** What people see while a new version of a graph loads into the graph store.

*Asked as:* What should people see while new data loads?

| Fact | Value |
|---|---|
| Key | `reads.mode` |
| Kind | One of: Always the latest (`latest`); Keep serving, update in place (`in_place`); Keep serving, switch when ready (`beside`) |
| Default | Always the latest · environment variable `GRAPHVER_READ_MODE` |
| Set at | Platform (system administrators), Workspace (workspace administrators), Graph (workspace administrators) |
| Limits | A system administrator can set the allowed choices or a lock. By default workspaces may choose Always the latest or Keep serving, update in place. |
| Takes effect | The next read of each graph. A save reaches every process within seconds. |

A publish or an import lands in the database at once, as one new version. Then the graph store, which answers reads fast, is updated, and on a large graph that takes a while. The read mode decides what readers get meanwhile: the newest version, read from the database; the graph store's copy as it is updated; or one whole version until a new copy is built and everyone switches to it.

**The choices**

- **Always the latest** (`latest`): Readers see the newest published version as soon as it is published. Until the graph store has it, they read it from the database. Before: Version 5, from the graph store. While: Version 6, from the database (the newest version, read from the database: slower, and without lineage summaries). After: Version 6, from the graph store. *Good for:* The default, and how reads have always worked. Small graphs, and graphs where the newest data matters more than speed. *Needs:* Database capacity for reads of whole graphs while they update.
- **Keep serving, update in place** (`in_place`): Readers stay on the graph store, at full speed, while the next version is written into the same copy. They may see part of it before the rest. Before: Version 5, from the graph store. While: Version 5, with parts of 6, from the graph store (version 5, with parts of 6 as they are written). After: Version 6, from the graph store. *Good for:* Large graphs whose views must stay fast while big imports land, where a moment of a partly applied change is fine. *Needs:* Nothing extra.
- **Keep serving, switch when ready** (`beside`): For a large change, readers keep exactly the version they have while the next one is built in a second copy, then everyone switches at once. Smaller changes are written in place. Before: Version 5, from the graph store. While: Version 5, from the graph store (exactly version 5; version 6 is built alongside). After: Version 6, from the graph store (switched in one step, once built and checked). *Good for:* Large graphs with big imports, where everyone should see one complete version at a time. *Needs:* New-version builds turned on, a platform copy rather than a connected graph, and free memory on a graph store node for a second copy.

**What it changes**

| Dimension | Better with | Worse with | Weight |
|---|---|---|---|
| Consistency | Always the latest and Switch when ready: readers see one whole version. | Update in place: readers can see part of a new version while it is written. | High |
| Read speed | Update in place and Switch when ready keep reads on the graph store at full speed. | Always the latest reads from the database during an update: slower on a large graph. | High |
| Update speed | Always the latest and Update in place show a change as it lands. | Switch when ready shows a large change only once it is built. | Medium |
| Memory | Always the latest and Update in place need no extra memory. | Switch when ready needs room for a second copy while it builds. | High |
| Database load | Update in place and Switch when ready keep reads off the database. | Always the latest sends every read during an update to the database. | Medium |
| Availability | Update in place and Switch when ready serve every read from the graph store. | Always the latest: under heavy load, a read from the database may be asked to retry. | Low |
| Cost | Always the latest and Update in place cost nothing extra. | Switch when ready needs spare memory on a graph store node. | Low |

**When to change it**

- Views of a large graph slow down for a while after each big import: choose Keep serving, update in place for that graph.
- Readers must never see part of an update: choose Keep serving, switch when ready, with New-version builds on and memory for a second copy.
- The newest data must show the moment it is published, even if slower: keep Always the latest.

**Recommended:** Always the latest. How reads have always worked: exact, with nothing extra to run. Set Keep serving, update in place on the large graphs whose views must stay fast, and Keep serving, switch when ready only where readers must see one whole version and there is memory for a second copy.

**Risk:** Medium. Keep serving, switch when ready needs New-version builds and room for a second copy, or it updates in place. Always the latest reads a graph that is updating from the database, which a busy database feels.

**Example:** With Always the latest, an import of 100,000 changes shows the moment it is published, read from the database until the graph store has it: slower on a large graph, and without lineage summaries meanwhile.

**Evidence:** Measured by the versioning-scale workflow (docs/versioning/09 §2) at 1,000,000 nodes and 1,000,000 edges, a change of 100,000 rows, 4 readers: Always the latest landed in 29 s, reads p99 66 ms, 5% of them from Postgres; update in place 30 s, p99 9 ms, no extra memory; switch when ready by a copy 56 s, p99 9.6 ms, FalkorDB at 2.0x the graph's memory at the peak; by a seed from Postgres 522 s, at 1.1x. No read failed in any mode. With 200 readers at 1M nodes and 2M edges, no read failed either: in run 43728972056 GRAPH.COPY took 76 to 88 s, past the projector's 75 s socket, and after 3 attempts the build was dropped and the change written in place; in run 43967953534 the copy took about 32 s and switch when ready landed by a switch, one whole version at a time. One rule applies the mode to every read: service.serving_seq with the lag build_policy.read_mode_for resolves for the graph (0 for latest). candidates.wanted builds beside only above buildAboveRows, on a platform-owned key, with candidateKeysEnabled on; a graph whose summaries live in a graph named from its key, or whose key other data sources read, is written in place (projection.\_keeps_its_key).

**Problems it answers:** Reads are slow while data loads; Canvases are slow after a big import; People see half-updated data; Lineage summaries are missing after an import; The database is busy after every publish.

**Also searched as:** read mode, consistency, freshness, stale reads, blue-green, hydration, serving while updating, projection, GRAPHVER_READ_MODE.

### `reads-maxVersionsBehind`

**Most versions behind.** How many versions behind the newest one a graph's copy may still serve readers while it catches up.

*Asked as:* How out of date may a fast view be while new data loads?

| Fact | Value |
|---|---|
| Key | `reads.maxVersionsBehind` |
| Kind | A whole number, 0 to 10,000, or unlimited |
| Default | Unlimited · environment variable `GRAPHVER_READ_MAX_LAG` |
| Set at | Platform (system administrators), Workspace (workspace administrators), Graph (workspace administrators) |
| Limits | A system administrator can set a range or a lock. |
| Needs | Read mode set to Keep serving, update in place or Keep serving, switch when ready. |
| Takes effect | The next read of each graph. A save reaches every process within seconds. |

With Keep serving, update in place or Keep serving, switch when ready, readers stay on the graph store's copy while it catches up, at the version it last finished. This caps how many versions behind that may be. Further behind, readers go to the database for the newest version until the copy catches up. Always the latest doesn't use it: it never serves an older version.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Consistency | Worse: Readers may see a version further behind the newest one. | Better: Readers get the newest version sooner, from the database when the copy is behind. | Medium |
| Read speed | Better: More reads stay on the fast graph store while it catches up. | Worse: More reads go to the slower database while the copy catches up. | Medium |
| Database load | Better: Fewer reads go to the database. | Worse: More reads go to the database while a graph catches up. | Medium |

**When to change it**

- Readers of a graph set to update in place must never be more than a few versions out of date: set a small number.
- Reads of a large graph go slow every time it falls behind: raise it, or set no limit.

**Recommended:** Unlimited. The copy catches up on its own, and until it does readers keep a whole recent version at full speed. A limit sends them to the database instead, which is slower on a large graph.

**Risk:** Low. A small limit sends readers of a busy graph to the database whenever it falls that far behind, which is slower and loads the database.

**Example:** A graph set to update in place keeps serving its copy, however many versions it falls behind, until it catches up.

**Evidence:** service.serving_seq: behind its head, a key serves main at the version it last published unless committed - held > lag; the lag is build_policy.read_mode_for's max_lag: 0 for latest, else this setting as it resolves for the graph (GRAPHVER_READ_MAX_LAG -1: any). The same bound decides whether a rebuild or a move can be built beside the key (service.\_beside_ok).

**Problems it answers:** Readers see data that is a few versions old; Reads are slow while data loads; The database is busy while a graph catches up.

**Also searched as:** max lag, staleness, versions behind, read lag, GRAPHVER_READ_MAX_LAG.

## Updates & loading

How new data is written into the graph store without slowing reads.

**With the defaults:** Each write to the graph store aims at 500 ms and stops at 10 seconds; after it, the worker pauses 25% of the write's time, or 200% while reads wait. A previous copy is kept 15 minutes after a switch or a move.

| Setting | Default | Set at |
|---|---|---|
| [Write target](#updates-statementtargetms) | 500 ms | Platform |
| [Longest write](#updates-writeceilingsecs) | 10 seconds | Platform |
| [Pause after a write](#updates-pacingratio) | 25% | Platform |
| [Pause while reads wait](#updates-readpressureratio) | 200% | Platform |
| [Keep the previous copy for](#updates-retiregracesecs) | 15 minutes | Platform |

### `updates-statementTargetMs`

**Write target.** How long each write to the graph store aims to take, so reads on the same node keep their turn.

| Fact | Value |
|---|---|
| Key | `updates.statementTargetMs` |
| Kind | Milliseconds, 100 to 10,000 |
| Default | 500 ms · environment variable `GRAPHVER_PROJECTION_STATEMENT_TARGET_MS` |
| Set at | Platform (system administrators) |
| Takes effect | The next write, once the worker reads its settings again, which it does as it updates each graph. |

While the worker writes new data into a graph's copy, every read of that graph on the same node waits for the write to finish. So writes are kept short: one that takes longer than this makes the next one smaller, down to 50 changes.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Read speed | Worse: Reads on the node can wait longer behind each write. | Better: Reads wait less behind each write. | High |
| Update speed | Better: Fewer, larger writes: a graph updates sooner. | Worse: More, smaller writes: a large update takes longer. | Medium |

**When to change it**

- Canvases stall for a moment, again and again, while a graph updates: lower it.
- Large updates take too long while reads are quiet: raise it.

**Recommended:** 500 ms. Short enough that a read waits about half a second at most behind a write, long enough that writes aren't split into tiny pieces.

**Risk:** Low. Too low splits writes into many small ones and slows large updates; too high makes reads wait behind long writes.

**Example:** Each write to the graph store aims to take about 500 ms. One that runs longer makes the next one smaller, so a read waits about that long at most behind a write.

**Evidence:** projection.\_laddered: a chunk slower than statementTargetMs halves the next, no narrower than 50 rows for being slow (\_SLOW_FLOOR). A write holds the graph's write lock, and every read of it on that node, while it runs (docs/versioning/04 §5, Serving while it updates).

**Problems it answers:** Canvases stall while a graph updates; Updates take too long to land.

**Also searched as:** statement target, write target, write batch, pacing, GRAPHVER_PROJECTION_STATEMENT_TARGET_MS.

### `updates-writeCeilingSecs`

**Longest write.** The longest one write to the graph store may run before it is stopped and split.

| Fact | Value |
|---|---|
| Key | `updates.writeCeilingSecs` |
| Kind | A time, 1 second to 1 minute |
| Default | 10 seconds · environment variable `GRAPHVER_PROJECTION_WRITE_CEILING_S` |
| Set at | Platform (system administrators) |
| Takes effect | The next write, once the worker reads its settings again, which it does as it updates each graph. |

A write still running after this long is stopped and sent again in halves, so no read waits longer than this behind one write. The graph store undoes a stopped write, so nothing is left half-written.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Read speed | Worse: A read can wait longer behind one write. | Better: No read waits long behind a write. | High |
| Update speed | Better: Fewer writes are stopped and redone: a heavy update lands sooner. | Worse: More writes are stopped and redone in halves: a heavy update takes longer. | Medium |

**When to change it**

- Reads freeze for several seconds during big updates: lower it.
- Updates of a large graph keep failing on timeouts: raise it a little.

**Recommended:** 10 seconds. Long enough for any well-sized write, short enough that a stuck write never holds a node's reads for long.

**Risk:** Medium. Set very low, writes that can't fit are halved down to one change and retried, and an update can fail.

**Example:** A write still running after 10 seconds is stopped and sent again in halves; reads behind it wait no longer than that.

**Evidence:** projection.\_laddered: every chunked write's budget is min(the client's write budget, writeCeilingSecs), on every FalkorDB mode; a timeout halves the chunk and sends the halves again, down to one row, then retries it 3 times (GRAPHVER_PROJECTION_FLOOR_RETRIES). FalkorDB rolls back a statement it aborts, and every projector write is an idempotent MERGE, SET or DELETE.

**Problems it answers:** Reads freeze during big updates; Updates fail with timeouts on a large graph.

**Also searched as:** write ceiling, write timeout, longest write, GRAPHVER_PROJECTION_WRITE_CEILING_S.

### `updates-pacingRatio`

**Pause after a write.** The pause after each write to the graph store, as a share of the time it took.

| Fact | Value |
|---|---|
| Key | `updates.pacingRatio` |
| Kind | A share, 0% to 500% |
| Default | 25% · environment variable `GRAPHVER_PROJECTION_PACING_RATIO` |
| Set at | Platform (system administrators) |
| Takes effect | The next write, once the worker reads its settings again, which it does as it updates each graph. |

After each write the worker pauses, so reads waiting on that node go first. At 25% it pauses a quarter as long as the write took, at most 5 seconds; at 0 it pauses only while reads are waiting (Pause while reads wait).

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Read speed | Better: Reads get more of the node's time while a graph updates. | Worse: Reads get less of the node's time while a graph updates. | High |
| Update speed | Worse: Updates take longer to land. | Better: Updates land sooner. | High |

**When to change it**

- Canvases are slow whenever a graph updates: raise it.
- Updates take too long while reads are quiet: lower it.

**Recommended:** 25%. Reads get a fifth of the node's time even while a graph updates, and updates still land quickly. While reads are waiting, the pause grows anyway (Pause while reads wait).

**Risk:** Low. High values slow every update; 0 lets a long update hold the node's reads.

**Example:** A write that takes 500 ms is followed by a 125 ms pause, so reads on that node get about 20% of its time while a graph updates.

**Evidence:** projection.\_pace: after each write a pause of pacingRatio times its time, readPressureRatio times while the web tier marks reads on the node as starving (agg:readpressure:\<node>), at most 5 s (\_PACE_MAX_S), none under 5 ms.

**Problems it answers:** Canvases are slow while a graph updates; Updates take too long to land.

**Also searched as:** pacing, pause, yield to reads, write rhythm, GRAPHVER_PROJECTION_PACING_RATIO.

### `updates-readPressureRatio`

**Pause while reads wait.** The longer pause after each write while reads on the node are waiting.

| Fact | Value |
|---|---|
| Key | `updates.readPressureRatio` |
| Kind | A share, 0% to 1000% |
| Default | 200% · environment variable `GRAPHVER_PROJECTION_READ_PRESSURE_RATIO` |
| Set at | Platform (system administrators) |
| Takes effect | The next write, once the worker reads its settings again, which it does as it updates each graph. |

When reads on a node are queueing, the worker pauses this share of each write's time instead, at most 5 seconds, so readers catch up. It applies only when it is longer than the usual pause.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Read speed | Better: Waiting reads catch up faster during an update. | Worse: Waiting reads stay queued longer. | High |
| Availability | Better: Fewer reads time out under load while a graph updates. | Worse: More reads may time out under load while a graph updates. | Medium |
| Update speed | Worse: An update slows more while reads are busy. | Better: An update keeps its pace while reads are busy. | Medium |

**When to change it**

- Reads time out or are asked to retry while a large graph updates: raise it.
- Updates stall during busy hours: lower it.

**Recommended:** 200%. While reads wait, each write is followed by a pause twice as long, so reads get two thirds of the node's time until they catch up.

**Risk:** Low. High values can hold an update back for as long as reads stay busy.

**Example:** While reads on a node are waiting, a write that takes 500 ms is followed by a 1,000 ms pause: reads get about 67% of the node's time until they catch up.

**Evidence:** projection.\_pace: readPressureRatio replaces pacingRatio while reads on the node are starving and it is the larger, at most 5 s; graphver_projection_yields_total counts each such pause.

**Problems it answers:** Reads time out while a graph updates; Updates stall during busy hours.

**Also searched as:** read pressure, starving reads, yield, GRAPHVER_PROJECTION_READ_PRESSURE_RATIO.

### `updates-retireGraceSecs`

**Keep the previous copy for.** How long a graph's previous copy is kept after a switch or a move, so reads under way finish on it.

| Fact | Value |
|---|---|
| Key | `updates.retireGraceSecs` |
| Kind | A time, 11 minutes to 1 day |
| Default | 15 minutes · environment variable `GRAPHVER_RETIRE_GRACE_SECS` |
| Set at | Platform (system administrators) |
| Takes effect | Switches and moves made after the change. A previous copy already waiting keeps the time it was given. |

When readers move to a new copy, after a new-version build or a move, the old copy stays in the graph store this long, so reads already running finish on it. Then it is removed and its memory freed. It is at least 11 minutes.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Memory | Worse: Old copies hold memory longer after each switch. | Better: Memory is freed sooner after a switch. | High |
| Availability | Better: Long reads under way at a switch always finish. | Worse: A read that started before a switch is likelier to fail when its copy is removed. | Medium |

**When to change it**

- Graph store memory stays high for a while after each switch or move: lower it.
- Long-running reads fail just after a switch: raise it.

**Recommended:** 15 minutes. Fifteen minutes is far longer than any read, and the memory comes back soon after.

**Risk:** Low. Long values keep two copies of a graph in memory after every switch; the graph store needs room for both.

**Example:** After a switch or a move, the previous copy stays 15 minutes; then it is removed and its memory freed.

**Evidence:** Stamped on retired_keys when a build switches (switch_to_candidate) or a key is moved: retireAfter = now + retireGraceSecs; the retire loop drops a due key once the new one has caught up. Its range starts at 660 s, past versioned_sources.CACHE_TTL_SECS (600 s), within which a newly versioned data source may still read its own key.

**Problems it answers:** Graph store memory stays high after a switch; Reads fail just after a switch or move.

**Also searched as:** retire grace, old copy, previous copy, GRAPHVER_RETIRE_GRACE_SECS.

### `builds-aboveRows`

**Build above.** How large a publish must be to be built in a second copy rather than written in place.

| Fact | Value |
|---|---|
| Key | `builds.aboveRows` |
| Kind | A whole number, 1,000 to 100,000,000 changes |
| Default | 200,000 changes · environment variable `GRAPHVER_PROJECTION_CANDIDATE_ABOVE` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | Publishes the worker starts updating after the change. A build already under way carries on. |

For a graph set to Keep serving, switch when ready, a publish that changes more than this many items is built in a second copy while readers keep the current version, then switched to. A smaller one is written into the current copy, paced, as with update in place.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Consistency | Worse: More publishes are written in place, where readers can see part of them. | Better: More publishes are built whole before readers see them. | Medium |
| Memory | Better: Fewer builds, so less room is taken by second copies. | Worse: More builds, each needing room for a second copy. | High |

**When to change it**

- Readers of a graph set to switch when ready see mid-sized imports half-applied: lower it.
- Builds keep the graph store short of memory: raise it.

**Recommended:** 200,000 changes. Builds are worth their memory for large changes, which take long enough to write that readers would notice. A change of 100,000 was written in place in about 30 seconds (measured).

**Risk:** Low. Very low builds a second copy for almost every publish, which takes memory and time.

**Example:** In a graph set to switch when ready, a publish of more than 200,000 changes is built in a second copy; one of 200,000 or fewer is written in place.

**Evidence:** candidates.wanted: read mode beside, the switch on, a platform-owned key and more version rows than buildAboveRows (counted no further, projection.\_queue_build). Measured (docs/versioning/09 §2): in place landed 100,000 rows into a 1M + 1M graph in 30 s, reads p99 9 ms.

**Problems it answers:** People see half-updated data after a mid-sized import; Builds use too much memory.

**Also searched as:** build threshold, build beside above, GRAPHVER_PROJECTION_CANDIDATE_ABOVE.

### `builds-forRebuilds`

**Rebuilds and moves too.** Whether rebuilds and moves of a graph set to switch when ready are built in a second copy too.

| Fact | Value |
|---|---|
| Key | `builds.forRebuilds` |
| Kind | On or off |
| Default | On · environment variable `GRAPHVER_PROJECTION_CANDIDATE_REBUILDS` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | Rebuilds and moves asked for after the change. One already under way carries on. |

On, a rebuild or a move of a graph set to Keep serving, switch when ready builds the new copy from the database while readers keep the current version, then switches. Off, they are made in place: a rebuild repairs the copy readers use as it goes, and a move builds the new copy from nothing while readers go to the database.

**What it changes**

| Dimension | Turning it on | Turning it off | Weight |
|---|---|---|---|
| Consistency | Better: Readers see one whole version through a rebuild or a move. | Worse: Readers see a rebuild's repairs as they happen. | Medium |
| Read speed | Better: Reads stay on the graph store during a move. | Worse: During a move, reads come from the slower database. | Medium |
| Memory | Worse: A rebuild needs room for a second copy while it is built. | Better: A rebuild needs no extra memory. | Medium |

**When to change it**

- Rebuilds of large graphs show partly repaired data, or moves send readers to the database for long: turn it on.
- The graph store has no room for second copies: turn it off.

**Recommended:** On. A rebuild or a move then never shows readers anything but a whole version, and reads stay fast.

**Risk:** Low. On, each rebuild or move of such a graph needs room for a second copy; without room it waits, or is made in place.

**Example:** A rebuild of a graph set to switch when ready builds a new copy from the database while readers keep the current version, then everyone switches.

**Evidence:** candidates.beside_wanted (beside, the switch on, buildForRebuilds on) and service.\_beside_ok (a live, platform-owned, idle key serving a version it published). A rebuild or a move is always seeded from Postgres, never copied (docs/versioning/04 §5, Rebuilds and moves built beside). In place, a rebuild keeps serving the version the key held (served_commit_seq), and a move's key, written from nothing, serves nothing until it is done.

**Problems it answers:** People see a graph being rebuilt; Reads are slow while a graph is moved.

**Also searched as:** rebuilds beside, moves beside, GRAPHVER_PROJECTION_CANDIDATE_REBUILDS.

### `builds-method`

**How a build makes its copy.** Whether a build copies the current copy or builds the new one from the database.

| Fact | Value |
|---|---|
| Key | `builds.method` |
| Kind | One of: Auto (`auto`); Copy only (`copy`); From the database only (`reseed`) |
| Default | Auto · environment variable `GRAPHVER_PROJECTION_CANDIDATE_MODE` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | The next time a build asks for room: a waiting build asks every minute. A build already copying or catching up carries on. |

A copy is fast, but needs about twice the graph's size free on the node the current copy is on. Building from the database is much slower, but needs about the graph's size, on whichever node has the most room. Auto copies when it can and builds from the database when it can't. Rebuilds and moves are always built from the database.

**The choices**

- **Auto** (`auto`): Copies the current copy when its node has room, else builds the new copy from the database on the node with the most room. *Good for:* Most platforms: the fastest build that fits.
- **Copy only** (`copy`): Always copies the current copy, waiting for room on its node. *Good for:* Platforms with plenty of memory on every node.
- **From the database only** (`reseed`): Always builds the new copy from the database, on the node with the most room. *Good for:* Nodes too full for copies, or graphs too large to copy in time.

**What it changes**

| Dimension | Better with | Worse with | Weight |
|---|---|---|---|
| Update speed | Auto and Copy only: a copy lands much sooner. | From the database only: each build reads the whole graph and takes much longer. | High |
| Memory | From the database only: about the graph's size, on the node with the most room. | Copy only: about twice the graph's size, on one node. | High |
| Database load | Auto and Copy only: a copy doesn't read the database. | From the database only: each build reads the whole graph from the database. | Medium |

**When to change it**

- Builds wait for room because the current copy's node is full: keep Auto, or choose From the database only.
- Copies of a very large graph time out: choose From the database only, or limit copies (Largest graph copied).

**Recommended:** Auto. The fastest build that fits: a copy when the node has room, else the database.

**Risk:** Low. Copy only waits as long as the node lacks room; From the database only is many times slower and reads the database hard.

**Example:** Auto: a build copies the current copy when its node has 220% of the graph's size free, else builds it from the database on the node with the most room.

**Evidence:** projection.\_build_queued: copy asks residency.admit_build_copy for room on the serving key's node; auto seeds (admit_build_seed, the master with most room) when the copy is refused for capacity or size; a rebuild or a move is always seeded. Measured (docs/versioning/09 §2): at 1M + 1M a change landed by GRAPH.COPY in 56 s at 2.0x the graph's memory at the peak, by a seed from Postgres in 522 s at 1.1x; at 100k + 100k, 14.5 s against 51.4 s.

**Problems it answers:** Builds wait for room; Builds take hours; Copies time out on a large graph.

**Also searched as:** build mode, copy or seed, GRAPH.COPY, reseed, GRAPHVER_PROJECTION_CANDIDATE_MODE.

### `builds-copyRoomPct`

**Free memory a copy needs.** The free memory a copy needs on its node, as a share of the graph's size.

| Fact | Value |
|---|---|
| Key | `builds.copyRoomPct` |
| Kind | A percentage, 100% to 400% |
| Default | 220% · environment variable `GRAPHVER_PROJECTION_COPY_MARGIN_PCT` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | The next time a build asks for room: a waiting build asks every minute. A build already copying or catching up carries on. |

While a copy is made, its node holds the new copy and the copy's own working buffer, each about the size of the graph. So a copy waits until the node has this share of the graph's size free under its start mark, and that room is held for it until it lands.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Availability | Better: A copy never pushes a node out of memory. | Worse: Under 200%, a copy can run a node out of memory, and every graph on it with it. | High |
| Memory | Better: Copies wait for more free memory, keeping nodes further from their limit. | Worse: Copies start with less free memory, closer to the node's limit. | High |
| Update speed | Worse: Builds wait longer for room, or are built from the database instead. | Better: Builds copy sooner. | Medium |

**When to change it**

- Memory alarms fire on a node while a copy runs: raise it.
- Builds wait for room though nodes have plenty free: lower it, never under 200%.

**Recommended:** 220%. A copy was measured at 2.0 times the graph's memory at its peak; 220% adds a margin.

**Risk:** High. Under 200%, a copy can take a node past its memory limit, which can stop every graph on that node.

**Example:** A copy of a 2 GB graph needs 4.4 GB free on its node, under the node's start mark.

**Evidence:** residency.copy_room: needed = size x copyMarginPct / 100 under the master's start mark after what is held there, reserved in the aggregation write governor's ledger under the capacity lock until the copy lands or fails. Measured (docs/versioning/09 §2): during GRAPH.COPY FalkorDB rose by 2.0x the graph's memory at its peak (1,324 to 3,910 MB at 1M + 1M; 1,463 to 4,447 MB at 1M + 2M); a seed from Postgres by 1.0 to 1.1x.

**Problems it answers:** Graph store memory alarms during a build; Builds wait for room.

**Also searched as:** copy margin, copy room, room a copy needs, GRAPHVER_PROJECTION_COPY_MARGIN_PCT.

### `builds-copyMaxBytes`

**Largest graph copied.** The largest graph a build may copy; a larger one is built from the database.

| Fact | Value |
|---|---|
| Key | `builds.copyMaxBytes` |
| Kind | A size, up to 16 TB, or unlimited |
| Default | Unlimited · environment variable `GRAPHVER_PROJECTION_COPY_MAX_BYTES` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | The next time a build asks for room: a waiting build asks every minute. A build already copying or catching up carries on. |

A graph over this size is never copied: with Auto its builds come from the database instead, which needs about half the memory but takes much longer; with Copy only they wait. Copies of very large graphs take long too, and one that outlasts the worker's wait on a write (75 seconds by default) fails that attempt.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Update speed | Better: Builds of large graphs land sooner, copied. | Worse: Builds of large graphs take much longer from the database. | High |
| Memory | Worse: Larger graphs are copied, at about twice their size. | Better: Large graphs are built from the database, at about their own size. | Medium |

**When to change it**

- Builds of large graphs take too long from the database while nodes have room: raise the limit, or remove it.

**Recommended:** Unlimited. Room for a copy is already checked first (Free memory a copy needs); set a limit when copies of your largest graphs time out.

**Risk:** Medium. With Copy only, a graph over the limit is never copied, so its builds wait.

**Example:** Any graph may be copied once its node has room.

**Evidence:** residency.copy_room refuses a graph larger than copyMaxBytes (too_large), and auto then seeds it (projection.\_build_queued). Measured (docs/versioning/09 §10, item 6): under 200 readers, GRAPH.COPY of 1M nodes and 2M edges took 76 to 88 s in run 43728972056, past the projector's 75 s socket (PROJECTION_FALKOR_WRITE_TIMEOUT_S 60 + PROJECTION_SOCKET_TIMEOUT_MARGIN_S 15); after 3 attempts the build was dropped and the change written in place. In run 43967953534 the same copy took about 32 s and landed. With 4 readers a copy of 1M nodes and 1M edges took about 19 s.

**Problems it answers:** Copies time out on a large graph; Builds of large graphs take hours.

**Also searched as:** copy limit, copy max bytes, GRAPHVER_PROJECTION_COPY_MAX_BYTES.

### `builds-noRoom`

**With no room.** What a build does when no node has room for it.

| Fact | Value |
|---|---|
| Key | `builds.noRoom` |
| Kind | One of: Wait for room (`wait`); Update in place (`in_place`) |
| Default | Wait for room · environment variable `GRAPHVER_PROJECTION_NO_ROOM_POLICY` |
| Set at | Platform (system administrators) |
| Needs | The New-version builds switch on. |
| Takes effect | The next time a waiting build asks for room, within a minute. |

Wait keeps readers on the current, whole version and asks again every minute, so the new version shows late when room is short. Update in place gives the build up and writes the change into the current copy, so it shows sooner but can be seen half-written.

**The choices**

- **Wait for room** (`wait`): Readers keep the current, whole version while the build waits; it asks for room again every minute.
- **Update in place** (`in_place`): The build is dropped and the change is written into the current copy, paced: readers may see it partly applied.

**What it changes**

| Dimension | Better with | Worse with | Weight |
|---|---|---|---|
| Consistency | Wait: readers only ever see whole versions. | Update in place: readers can see the change partly applied. | High |
| Update speed | Update in place: the change shows without waiting for room. | Wait: the change shows only once there is room for a build. | High |

**When to change it**

- New versions sometimes don't show for hours because nodes are full: choose Update in place, or add memory.
- Readers must only ever see whole versions: keep Wait.

**Recommended:** Wait for room. Readers keep a whole version, and an alert says when a build is stuck (Alert after waiting).

**Risk:** Medium. With Wait, a change can stay hidden from readers for as long as nodes lack room.

**Example:** With no room, a build waits, asking again every minute, while readers keep the current version; after 30 minutes it raises an alert.

**Evidence:** projection.\_build_queued: wait records why and retries after 60 s; in_place raises \_BuildRefused and drop_candidate writes the window in place. A rebuild the projector started on its own never waits for room: it is made in place.

**Problems it answers:** A new version never shows up; Builds wait for room; People see half-updated data.

**Also searched as:** no room policy, waiting for room, GRAPHVER_PROJECTION_NO_ROOM_POLICY.

### `residency-class`

**Residency class.** Whether a graph stays in the graph store's memory when nobody reads it.

*Asked as:* Should graphs stay ready in memory when nobody is using them?

| Fact | Value |
|---|---|
| Key | `residency.class` |
| Kind | One of: Always (`always`); Standard (`standard`); Coldline (`coldline`) |
| Default | Standard · built in |
| Set at | Platform (system administrators), Workspace (system administrators), Graph (system administrators) |
| Needs | The Graph residency switch on. |
| Takes effect | The next memory check, within a minute: an Always graph not in memory is queued to load, and a Standard or Coldline graph may be unloaded once idle. |

With Graph residency on, the graph store keeps each graph by its class and each node's memory. Always graphs are never unloaded. Standard graphs are unloaded after a long time unread, or sooner when memory runs short, and load again on their next read. Coldline graphs are unloaded soon after use and are usually read from the database. A connected graph is never unloaded, whatever its class. Unloading loses nothing: the database holds every version, and a graph that isn't loaded is read from it, more slowly.

**The choices**

- **Always** (`always`): Never unloaded. If it isn't in memory, it loads as soon as there is room. *Good for:* Graphs people open first thing every day, or that must open fast at any hour.
- **Standard** (`standard`): Unloaded after a long time unread, a week by default, or sooner when its node runs short of memory. Loaded again on its next read. *Good for:* Most graphs.
- **Coldline** (`coldline`): Unloaded soon after use, an hour unread by default, and first when memory runs short. Read from the database until something needs it loaded. *Good for:* Archives and graphs opened now and then.

**What it changes**

| Dimension | Better with | Worse with | Weight |
|---|---|---|---|
| Read speed | Always: every read is fast. | Coldline: most reads come from the slower database. | High |
| Memory | Coldline: memory is used only while a graph is in use. | Always: memory is held whether the graph is read or not. | High |
| Database load | Always and Standard: reads stay off the database. | Coldline: reads go to the database until the graph is loaded. | Medium |
| Cost | Coldline: less memory, so a smaller graph store. | Always: memory for the graph at all times. | Medium |

**When to change it**

- A graph people open first thing every day is slow to open: make it Always.
- A rarely used graph holds memory other graphs need: make it Coldline.
- Most graphs: keep Standard.

**Recommended:** Standard. Graphs people use stay fast, and ones nobody reads give their memory back. Keep Always for the few that must open fast at any hour.

**Risk:** Medium. Too many Always graphs can leave no room to load others, whose readers then wait on the database.

**Example:** A Standard graph nobody reads for 7 days is unloaded; its next read comes from the database and loads it again.

**Evidence:** residency_plan.plan: idle eviction by class (standard_idle_secs, coldline_idle_secs), pressure eviction Coldline first, then Standard by oldest read; never an Always graph, a key the platform did not mint, a leased graph, or one with a pass or a window in flight. residency.mark: a person's read asks for the load of a Standard or Always graph, and of a Coldline graph with more entities than coldlineCanvasLoadAbove. Each graph's class in force is kept on projection_state.residency, which the evictor's guard reads: a new graph gets it, a save writes it to the graphs it reaches, and each capacity pass puts it back in step first (residency.keep_classes; docs/versioning/17 §10 to §12).

**Problems it answers:** A graph is slow to open after a quiet spell; Graph store memory alarms; A rarely used graph takes memory others need.

**Also searched as:** residency, class, Always, Standard, Coldline, keep loaded, eviction class, defaultResidency.

### `residency-autoUnload`

**Unload graphs automatically.** Whether the graph store unloads graphs on its own.

| Fact | Value |
|---|---|
| Key | `residency.autoUnload` |
| Kind | On or off |
| Default | On · environment variable `GRAPHVER_EVICTION_ENABLED` |
| Set at | Platform (system administrators) |
| Needs | The Graph residency switch on. |
| Takes effect | The next memory check, within a minute. |

On, each memory check unloads graphs left unread past their class's idle time, and graphs on a node past its start mark until it is back at the stop mark. Off, nothing is unloaded, not even to make room for a load: graphs not in memory load only where there is room.

**What it changes**

| Dimension | Turning it on | Turning it off | Weight |
|---|---|---|---|
| Memory | Better: Unused graphs give their memory back. | Worse: Every loaded graph keeps its memory. | High |
| Availability | Better: Nodes are kept under their memory marks. | Worse: A node can fill up, and graphs waiting to load go on waiting. | High |
| Read speed | Worse: A graph unloaded after a quiet spell is slower on its next read. | Better: Loaded graphs stay fast. | Medium |

**When to change it**

- Graphs unload in the middle of the working day and people notice: raise the idle times or use Always, rather than turning this off.
- You are looking into unloads and want them to stop for a while: turn it off.

**Recommended:** On. Memory is what the graph store runs short of; unloading unused graphs keeps room for the rest.

**Risk:** Medium. Off, a full node stays full: new and unloaded graphs wait to load, and their readers stay on the database.

**Example:** Standard graphs unread for 7 days and Coldline graphs unread for 1 hour are unloaded, and a node past 80% of its memory unloads graphs until it is at 70%.

**Evidence:** residency_plan.\_plan_master: idle and pressure eviction only with eviction_enabled, and \_make_room returns False without it. The capacity pass evicts nothing in the 90 s grace after Graph residency is turned on (residency_policy.GRACE_SECS). While the settings can't be read, before the first read or since one failed, eviction is off and loads go on (residency_policy.resolve).

**Problems it answers:** Graph store memory alarms; Graphs unload unexpectedly; Graphs wait to load.

**Also searched as:** eviction, auto unload, unload, GRAPHVER_EVICTION_ENABLED.

### `residency-standardIdleSecs`

### `residency-unloadStartPct`

**Start unloading at.** The share of a node's memory at which graphs start to be unloaded; loads and copies must fit under it.

| Fact | Value |
|---|---|
| Key | `residency.unloadStartPct` |

When a node uses this share of its memory or more, the next memory check unloads graphs there, Coldline first, then Standard by oldest read, until it is back at the stop mark. Loads and copies start only if they fit under this mark, so a load never pushes a node into unloading what it just loaded.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Availability | Worse: Less room for a sudden peak above the mark. | Better: More room for peaks. | High |

**Problems it answers:** Graph store memory alarms; Graphs unload while people use them; Loads wait for room.

**Also searched as:** high water, start mark, memory pressure, GRAPHVER_MASTER_HIGH_WATER_PCT.

### `database-readTimeoutMs`

**Longest read.** The longest one read of a graph from the database may run.

| Fact | Value |
|---|---|
| Key | `database.readTimeoutMs` |

| Default | 15 seconds · environment variable `GRAPHVER_READ_STATEMENT_TIMEOUT_MS` |
| Set at | Platform (system administrators) |
| Takes effect | The next read from the database. |

**Risk:** Low. Very short, large graphs can't be read from the database at all; very long, slow reads crowd it.

**Example:** While a graph is read from the database, a read running over 15 seconds is stopped and the reader asked to retry.

**Evidence:** db.bounded_read_sessions sets statement_timeout to pgStatementTimeoutMs on each session; a cancelled read answers 503 graph_read_busy, retryable, counted in graphver_pg_read_timeouts_total.

### `imports-identifier`

**Match rows by.** What an import's rows find existing items by, when the import doesn't say.

*Asked as:* How should imports find the items that already exist?

| Fact | Value |
|---|---|
| Key | `imports.identifier` |
| Kind | `entity_id`, `urn`, `prop.<name>` or `prop.<name>,urn` |
| Default | `entity_id` · environment variable `GRAPHVER_IMPORT_IDENTIFIER` |
| Set at | Platform (system administrators), Workspace (workspace administrators), Graph (workspace administrators) |
| Limits | A system administrator can set a lock. |
| Takes effect | Imports started after the change. An import already running keeps the settings it started with. |

Entity ID finds an item by its id, then its URN, its identifier property, a field its type is matched by, or a unique qualified name. URN finds it by its id or URN only. A property finds it by its id or that property's value; a property then URN falls back to the URN for rows without the value. A row that finds nothing makes a new item, so the wrong choice makes duplicates, and a replace import deletes what it didn't find.

**What it changes**

| Dimension | Better with | Worse with | Weight |
|---|---|---|---|
| Consistency | An identifier every row carries, such as the URN or your source system's id, matches rows to the same items every time. | An identifier the rows don't carry matches nothing, so each import makes new items. | High |
| Database load | Entity ID and URN need no index. | A property needs an index of its values, built by the first import that uses it. | Low |

**When to change it**

- Imports make duplicates instead of updating items: match by the identifier your files carry, such as the URN or a property from your source system.
- Your source system has its own ids: match by that property.

**Recommended:** `entity_id`. It finds items by everything the platform knows them by: their id, URN, identifier property and the fields their type is matched by.

**Risk:** High. An identifier the files don't carry matches nothing: an update makes duplicates, and a replace would delete the graph and make it again. The replace guard stops most such imports.

**Example:** Rows find existing items by their id, then their URN, their identifier property, a field their type is matched by, or a unique qualified name.

**Evidence:** import_export/identifier.py: entity_id, urn, prop.\<name> or prop.\<name>,urn; import_settings.for_import: the request's, else the graph's, else its workspace's, else the platform's (GRAPHVER_IMPORT_IDENTIFIER until one is set), kept on the job. A fork follows its root, but can't match by a property yet, so its default property is entity_id there (docs/versioning/08 §3b).

**Problems it answers:** Imports create duplicates instead of updating; Imports deleted too much; Imports match the wrong items.

**Also searched as:** identifier, match by, alternate key, external id, GRAPHVER_IMPORT_IDENTIFIER.

**Example:** An import with any refused row holds: a replace deletes nothing, and an import set to publish itself waits for review.

**Evidence:** import_worker.refused_budget and within_budget: 0, a count, a share ('0.5%') or -1; an invalid platform value holds on any refused row. The request's, else this setting as it resolves for the graph when the import is made (import_settings.for_import), kept on jobs.import_settings (docs/versioning/08 §3b).

**Problems it answers:** Imports stop on a few bad rows; Imports publish with rows missing.

**Also searched as:** refused rows, bad rows, maxRefusedRows, IMPORT_MAX_REFUSED_ROWS.

### `imports-maxMatchingProperties`

**Matching properties per graph.** How many properties one graph's imports may match items by.

*Asked as:* How many properties may imports match items by?

| Fact | Value |
|---|---|
| Key | `imports.maxMatchingProperties` |
| Kind | A whole number, 0 to 100 properties |
| Default | 10 properties · environment variable `GRAPHVER_MAX_MATCHING_PROPERTIES` |
| Set at | Platform (system administrators) |
| Takes effect | The next import that matches by a property not indexed yet. Properties already indexed are kept. |

Matching by a property keeps an index of its values in the database: built by the first import that names it, reading every item once, then kept up to date by each import that uses it. One property past this number is refused. 0 allows no new property.

**What it changes**

| Dimension | Raising it | Lowering it | Weight |
|---|---|---|---|
| Database load | Worse: More indexes to build and keep up to date. | Better: Fewer indexes to build and keep up to date. | Medium |
| Cost | Worse: More database space for indexes. | Better: Less database space for indexes. | Low |

**When to change it**

- A data source needs to match by more of its source systems' ids: raise it.
- Index builds weigh on the database: lower it.

**Recommended:** 10 properties. Enough for the ids several source systems carry, without an index for every property.

**Risk:** Low. Lowering it never removes an index; it only refuses new properties.

**Example:** Each graph's imports may match items by up to 10 properties, each kept in an index.

**Evidence:** import_export/keys.ensure: a property not indexed yet is refused (too_many_matching_properties) when the graph already has as many others as its limit: the import's job keeps it (import_settings.for_import), else the platform's value of this setting; the index is built from main's live nodes a page at a time, minutes at a million nodes (docs/versioning/08 §3b).

**Problems it answers:** Imports can't match by another property; Imports by a new property are slow to start.

**Also searched as:** matching properties, alternate keys, external ids, GRAPHVER_MAX_MATCHING_PROPERTIES.

## Glossary

| Term | What it means | Technical details |
|---|---|---|
| **Graph store** | Where each graph's latest version is held in memory, so reads are fast. | FalkorDB. Each versioned graph's published main is projected into a key there; Postgres stays the source of truth. |
| **Database** | Where every version of every graph is kept for good. It is the source of truth, so nothing is lost when a graph is unloaded. | Postgres: the graphver schema, on GRAPHVER_DB_URL or the management database. |
| **Copy** | A graph's latest version in the graph store, which readers read. | A FalkorDB key (projection_state.falkor_graph_name). |
| **Platform copy** | A copy the platform made and manages: it can be unloaded, loaded, moved and built beside. | owns_falkor_graph is true: a key the platform minted. |
| **Connected graph** | A graph read from a copy its owner keeps in their own graph store. The platform never unloads it, copies it or builds beside it. | A customer's own FalkorDB key with version control enabled (owns_falkor_graph false), until it is adopted onto a platform key. |
| **Version** | One published state of a graph. Each publish, merge or import makes a new one. | A commit on main (commit_seq). |
| **Updating** | Writing a new version into a graph's copy. | A projection pass: the projector writes a window of version rows and advances the watermark (projected_commit_seq). |
| **Loading** | Bringing a graph that isn't in memory back into the graph store. | Rehydration: a full seed of a fresh key from Postgres, admitted by the capacity loop (status rehydrating). |
| **Unloading** | Removing a graph's copy from the graph store to free memory. Nothing is lost: until it is loaded again, it is read from the database. | Eviction (CacheManager.evict): the key is dropped and the graph marked evicted, with why. |
| **New-version build** | Building a graph's next version in a second copy while readers keep the current one, then switching. | A candidate key (projection_state.candidate\_\*), made by GRAPH.COPY or seeded from Postgres, caught up, checked, then switched to (docs/versioning/04 §5). |
| **Switch** | The moment readers move from the current copy to a newly built one, all at once. | switch_to_candidate: one transaction repins the graph to the build's key; the old key joins retired_keys. |
| **Read mode** | What readers see while a new version of a graph loads: Always the latest, Keep serving, update in place, or Keep serving, switch when ready. | build_policy.read_mode_for, per graph, applied by service.serving_seq with the mode's lag cap. |
| **Residency class** | Whether a graph stays in memory when nobody reads it: Always, Standard or Coldline. | projection_state.residency. |
| **Always** | A residency class: never unloaded. | residency 'always'; the evictor refuses it. |
| **Standard** | A residency class: unloaded after a long time unread, or sooner when memory runs short, and loaded again on its next read. | residency 'standard'. |
| **Coldline** | A residency class: unloaded soon after use, and usually read from the database. | residency 'coldline'. |
| **Node** | One server of the graph store, with its own memory. | A FalkorDB cluster master, or a standalone or Sentinel-managed instance. |
| **Start mark** | The share of a node's memory at which graphs start to be unloaded; loads and copies must fit under it. | high_water_pct of maxmemory. |
| **Stop mark** | The share of a node's memory down to which graphs are unloaded. | low_water_pct of maxmemory. |
| **Memory check** | The regular check, every minute by default, of each node's memory, which unloads and loads graphs. | residency.CapacityLoop.run_once: one leader across workers, under a Postgres advisory lock. |
| **Worker** | A background process that updates graphs and runs builds, imports and sweeps. | The versioning worker (python -m backend.app.services.versioning), by lanes: projection, transfer and bootstrap. |
| **Lineage summaries** | Counts of lineage between containers, kept ready so large views open fast. | :AGGREGATED rollup edges, built by the aggregation job and moved by the projector. |
| **Draft** | A set of changes to a graph that isn't published yet. | A branch of kind draft. |
| **Review** | A request to merge a draft, which reviewers approve. | A merge request. |
| **Fork** | A separate copy of a graph to work in, which reads through the original. | A graph with fork_parent_graph_id and no FalkorDB key of its own (docs/versioning/17). |
| **Trash** | Where a deleted data source waits, restorable, before it is removed for good. | A tombstone (deleted_at); the reaper queues its purge after PURGE_GRACE_DAYS. |
| **Replace import** | An import that makes the graph, or a view's part of it, match the file: what the file leaves out is deleted. | reconcileMode=replace. |
| **Identifier** | What an import's rows find existing items by. | identifier: entity_id, urn, prop.\<name> or prop.\<name>,urn. |
| **Matching property** | A property imports can find items by, kept in an index of its values. | graphver.entity_keys and key_index (import_export/keys.py). |
| **Default** | The value in force where no level chose one: the deployment's environment variable if it is set and valid, else the built-in value. | settings_types.Default(code, env, attr). |
| **Platform** | A value for the whole platform, chosen by a system administrator. | scope platform, scope_id ''. |
| **Workspace** | A value for every graph in one workspace, chosen by its administrators where they may. | scope workspace, scope_id the workspace id. |
| **Graph** | A value for one data source's graph. A fork follows the graph it was forked from. | scope graph, scope_id the data source id. |
| **Limit** | What a system administrator lets workspace administrators choose: the allowed choices, a range, or a lock. | setting_values.limits on the platform row. |
| **Exception** | A value a system administrator set outside the limits. It stays in force, marked as an exception, so tightening a limit never changes a graph without anyone noticing. | Resolver status exception. |

## Set by your deployment

These are set by environment variables only, because they size the deployment itself. The app shows each one read-only, with the value the workers report, beside the settings it bounds. Every environment variable, with its default, is in the [Configuration Reference](/docs/configuration).

| Variable | Shown under | What it sets |
|---|---|---|
| `GRAPHVER_ROUTE_CACHE_SECS` | Reads & consistency | **Where reads go, kept for.** How long a process may go on sending a graph's reads where it last looked, to its copy or to the database, before looking again. A write tells every process at once, so this only bounds a change that couldn't be announced. |
| `GRAPHVER_PROJECTION_CONCURRENCY` | Updates & loading | **Graphs each worker updates at once.** How many graphs each worker updates at once. Builds count among them, so it also caps Builds per worker. |

| `GRAPHVER_PROJECTION_PASS_MAX_SECS` | Updates & loading | **Longest turn of one graph.** A large update stops at a page boundary after this long and carries on in its next turn, so other graphs get theirs. |
| `GRAPHVER_PROJECTION_INLINE_MAX_ROWS` | Updates & loading | **Written straight after a publish, up to.** A change up to this size is written into the graph store straight after its publish; a larger one by the worker. It is also the default of Changes left at the switch. |
| `PROJECTION_FALKOR_WRITE_TIMEOUT_S` | New-version builds | **Longest wait on one write.** How long the worker waits on one write to the graph store. A copy waits this plus 15 seconds, 75 by default, and one that takes longer fails that attempt. |
| `GRAPHVER_TRACE_LEASE_TTL_SECS` | Memory & residency | **A read holds its graph for.** How long a person's read keeps its graph from being unloaded. |
| `GRAPHVER_POOL_SIZE` | Database reads | **Database connections per process.** Connections each process keeps for versioned graphs. Reads at once per process should stay under it. |
| `GRAPHVER_POOL_MAX_OVERFLOW` | Database reads | **Extra connections at a peak.** Connections a process may open past its pool at a peak. |
| `GRAPHVER_ROUTE_POOL_SIZE` | Database reads | **Connections for finding where reads go.** A small pool of its own that finds where each read goes, so heavy reads can't stop that. |
| `GRAPHVER_DRAFT_SWEEP_SECS` | Drafts & history | **Draft sweep every.** How often the worker closes idle drafts and removes closed drafts' changes. |
| `GRAPHVER_REAP_POLL_SECS` | Drafts & history | **Trash check every.** How often the trash is checked for data sources past their restore window. |
| `GRAPHVER_FORK_REWIND_MAX` | Drafts & history | **Most changes a fork reads through.** Changes a fork and the graph it came from may have made since they parted before the fork's reads go to the database. |
| `IMPORT_COMMIT_WINDOW` | Imports | **Rows per import step.** Rows an import saves to its draft at a time; the early stop decides after the first such step. |
| `GRAPHVER_TRANSFER_SLOTS` | Imports | **Jobs per worker.** Import, export and publish jobs each worker runs at once. |
| `IMPORT_STAGING_GC_DAYS` | Imports | **Staged rows kept for.** Days a finished import's staged rows are kept, to resume or re-run it. |
