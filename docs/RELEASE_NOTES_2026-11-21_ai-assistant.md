# An assistant that reads your lineage as you do, and asks before it guesses — 2026-11-21

People asked for one thing in many forms: *let me ask my lineage questions in plain words*.

- "What are the downstream consumers of the *suppliers* dataset, and what breaks if it is removed?"
- "If `first_name` in table A is dropped, who is affected, why, and when?"
- "Which tables hold PII, and were any of them updated last week?" — then "do any of those feed my
  datasets in domain A?"
- "Do we have views about supply-chain failures?"
- "How do I share a view?"
- And from other teams: "let our agents read your knowledge."

The platform already had the hard parts: a validated, view-scoped search language, a lineage walk
that pages through millions of edges, rolled-up lineage for breadth, a property catalogue, and
deny-by-default API keys. This release puts an assistant on top of them, rather than beside them.

> **Operator action:** a migration runs with the upgrade (`20261121_1000_ai_assistant`), and two
> services are new: `ai-service` and `vectordb`. Nothing reaches a model until an administrator
> turns on **AI assistant** and connects one. See [§4](#4-rollout).

## 1. What it does

- **Ask about data** — answers from the views and data sources the person can read, as cards:
  results (counts by type and container), impact and provenance reports, searches, view
  suggestions. Every answer shows *How I got this*.
- **Help** — answers about using the product from the docs and user guide, with citations that
  open the exact section; plus any knowledge sources an administrator connects over MCP.
- **Ask AI** in Advanced Search and **Draft with AI** in the Cypher tab.
- **Administration → AI** — connections, data sharing, limits, retention, knowledge, vocabulary,
  usage.
- **Knowledge MCP** — `POST /api/v1/ai/mcp/knowledge` for other teams' agents.

## 2. How accuracy is protected

1. **Structured, validated queries.** The model writes the platform's own search predicates; each
   is validated by the platform's model (an unknown field is an error, never silently dropped) and
   counted before anyone sees it. Cypher is guard-checked and run only by the person.
2. **Deterministic playbooks** for impact and provenance: the same question gets the same report.
3. **Asking, not guessing.** A business term is matched against the data with counts; one exact,
   unambiguous match is used and said; anything else is a choice for the person, remembered if
   they wish.
4. **Exact counts at any size.** A walk cut at its node budget is followed by an exact count
   from a search walked from the target; rolled-up lineage gives the breadth, and the report says
   which grain each number came from.
5. **No invented metadata.** No owner, schedule or transformation appears that the metadata does
   not record, and the report says when it records none.

## 3. How access is protected

- The assistant has **no data access of its own**. Every read goes back through the platform API
  with a **read-only delegation** minted per request (ADR-032): the API key surface, the resource
  fence, the person's live claims, views and data `read` only. Refused on writes, on native
  queries, after the session ends, when the switch is off; never wider than an API key it came
  with.
- Every outbound call is held to the shared **network guard**: no loopback or cloud metadata, no
  private host an operator has not listed, no plain http in production, no redirects.
- **Data sharing** under Administration → AI decides whether descriptions, property values and
  sample values may reach the model, how many rows, and what is redacted.
- The **activity log** records that a question was asked and where — never its text.

## 4. Rollout

1. Upgrade (the migration adds the `ai_*` tables and grants `workspace:ai:use` to every role
   that reads data sources).
2. Deploy `ai-service` and `vectordb` (Compose services; Kubernetes `services/ai-service` and
   `infrastructure/vectordb`; Helm `services.ai`). Or point `AI_VECTOR_DB_URL` at a managed
   Postgres with pgvector, or leave it unset for keyword-only retrieval.
3. Set `AI_INTERNAL_TOKEN` to the same value on viz-service and ai-service (generated by
   `deploy/k8s/deploy.sh setup`; required with `ENV=production`).
4. For a model on your private network, list its `host:port` in `AI_EGRESS_ALLOWED_HOSTS`; in Helm,
   allow its range in `networkPolicy.aiEgressCidrs`.
5. Optional: create a read-only service account and set its key as `AI_INDEXER_API_KEY` to embed
   the views catalogue.
6. In the app: **Administration → Features → AI assistant** on; **Administration → AI →
   Connections**, add and **Test**; **Assistant**, choose it.

## 5. Verification

- `GET /health` on the AI service answers `healthy`.
- **Test connection** reports *answer*, *tools* and (with an embedding model) *embeddings*.
- **Knowledge** shows `docs` ready (or lexical) and, with the service account, `views` ready.
- Ask *How do I share a view?* in **Help** — a cited answer. Ask *What breaks if … is removed?* on a
  view — an impact report.
- Backend tests: `test_ai_llm.py`, `test_ai_agent.py`, `test_ai_agent_units.py`,
  `test_ai_knowledge.py`, `test_ai_delegation.py`.

## 6. Not in this release

- Provider kinds beyond OpenAI-compatible (Anthropic, Bedrock, Vertex, a custom HTTP template).
- Entity-level semantic matching (designed: selective by type, opted in per data source).
- Data-plane MCP tools (search, trace, impact) for other teams' agents.
- Questions across several data sources at once; Neo4j and Spanner closure walks.
